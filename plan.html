Interactive web-planner: MCP + planner agent

scope: this project decisions locked

Summary

Build an MCP server + planner agent that own the whole planning experience. Plans are Preact .plan.tsx files composed of annotatable blocks, diagram-heavy via Mermaid. Claude never ends a turn — it blocks on wait_for_message after every response, behaving like a persistent chat partner. Users send messages from the browser chat or from the terminal CLI, drop a single short comment on any block, and click Send feedback to wake the planner for a revision. Once a plan is marked implemented, it's frozen — historical record only.

Locked-in choices

  • Runtime: Node + TypeScript
  • Agent wiring: top-level mode via /web-plan slash command
  • Framework: Preact + a small component kit; plans authored as .plan.tsx
  • Diagram tool: Mermaid (switched from Excalidraw — see "Why Mermaid" below)
  • Block kinds: open-ended; per-project components.tsx + components.css for new kinds
  • Browser transport: SSE for push, plain POST for everything else
  • Comments: at most one short comment per block. No author, no likes, no replies. Replacing it overwrites; the popover never grows.
  • Plan storage root: ~/.web-planner/ — same global root as the existing skill's directory pattern.
  • Plan immutability: plans with status implemented are frozen. proposed and approved (in-progress / not-accepted) are editable. Nothing is ever removed.
  • Wait timeout: wait_for_message never times out
  • Host/port: http://localhost:1248
  • Layout: Obsidian-style readable column (~740px) inside a wider page (~980px)
  • v1 component kit: 11 components — see "Component kit" section
  • Installer prompts: 8 prompts — see "Interactive installer" section
  • Version control: Jujutsu (jj). Commit at logical checkpoints during implementation. No pushing.

Why Mermaid over Excalidraw

Excalidraw's data model is hand-positioned shapes in pixel space — to author from a semantic description we'd have to build a graph-layout compiler (dagre/elk) that emits Excalidraw JSON. Excalidraw's real strength is interactive, hand-drawn editing, which is wasted on read-only plan renders. Mermaid is text-in / SVG-out: Claude writes five lines of fenced sequenceDiagram and gets a labeled, auto-laid-out diagram. It covers every diagram shape we care about (sequence, flowchart, state, ER, gantt, class, timeline, mindmap), has theme support, and ships an ESM build we can lazy-load only on plan pages that contain a diagram. We keep the option to embed a raw SVG block for the rare case Mermaid can't draw it.

Goals

  • Persistent planner loop. Outer loop is while true: msg = wait_for_message(); ….
  • Plans are .plan.tsx, server-compiled to HTML on read via esbuild's transformer + a Preact SSR pass.
  • Diagram-first. Structural content prefers a <Mermaid> block over prose.
  • Component kit + per-project extensions. Eleven built-in components; new kinds register in ~/.web-planner/projects/<slug>/components.tsx.
  • One comment per block. No author, no likes, no replies. Adding a comment to a block that already has one replaces it.
  • Implemented plans are frozen. Editing tools refuse on status implemented; new comments are blocked too. Plans live forever — never removed.
  • Obsidian-style reading width. Prose at ~740px; diagrams escape into a wider column.
  • Live state surface. Pill in dashboard, wp status in CLI.

The blocking primitive

// shared
async function awaitInput(kind, payload) {
  const id = randomUUID();
  state.setActivity({ kind, id, payload, since: Date.now() });
  sse.broadcast({ type: kind + ":open", id, payload });
  return new Promise((resolve) => {
    state.pending.set(id, { resolve, kind });
  });
}

// MCP tool: wait_for_message — no timeout
async function wait_for_message() {
  const msg = await awaitInput("message", {});
  return { content: [{ type: "text", text: msg.text }] };
}

// MCP tool: ask_user
async function ask_user({ questions, timeout_seconds = 1800 }) {
  const answers = await awaitInput("ask_user", { questions, timeout_seconds });
  return { content: [{ type: "text", text: formatAnswers(answers) }] };
}

// HTTP endpoints that unblock the planner
POST /api/message            // browser chat or `wp send`
POST /api/answer/:id         // ask_user response
POST /api/feedback           // bundled comments + likes

Plans = Preact blocks

A plan is a Preact module that default-exports a <Plan> built from <Block> children. The block id is stable across edits; the block kind is a free-form slug Claude picks. Built-in components live in @web-planner/kit; per-project extensions live in ~/.web-planner/projects/<slug>/components.tsx. 

// example plan source
import { Plan, Block, Callout, StepList, FileList, Mermaid, Arch } from "@web-planner/kit";
import { DbSchema } from "../../components"; // per-project extension

export default () => (
  <Plan title="Add OAuth login" status="proposed">
    <Block id="b-summary" kind="summary">
      <Callout>Add Google OAuth as the first login provider.</Callout>
    </Block>

    <Block id="b-arch" kind="diagram.sequence">
      <Mermaid>{`
        sequenceDiagram
          User->>App: /login
          App->>Google: redirect
          Google-->>App: code
          App->>Session: create
      `}</Mermaid>
    </Block>

    <Block id="b-files" kind="files">
      <FileList items={[
        { path: "src/auth/oauth.ts", desc: "new — Google flow" },
        { path: "db/migrations/0042_session.sql", desc: "schema bump" },
      ]} />
    </Block>

    <Block id="b-schema" kind="db.schema">
      <DbSchema tables={[ /* … */ ]} />
    </Block>

    <Block id="b-steps" kind="steps">
      <StepList steps={[
        { title: "Migration", text: "Add sessions table." },
        { title: "OAuth client", text: "Wire passport-google-oauth20." },
      ]} />
    </Block>
  </Plan>
);
Token wins compound: a 12-step plan that would be ~400 lines of HTML is ~50 lines of JSX. Auto-import lint catches typos at plan-write time. The <Block> wrapper handles the like + comment chrome for every block regardless of kind, so new kinds get full functionality for free.

Server-side validation on create_plan / update_block

  • Parses with esbuild — syntax errors return a clear tool error.
  • Every <Block> must have a unique id.
  • create_plan / update_block / append_block that target a plan with status implemented are rejected with plan_frozen.
  • A write that drops a block id with an existing comment is rejected — the agent must address or carry the comment forward.
  • Component imports outside @web-planner/kit + the project's components.tsx are rejected.

Per-project extensions

├── components.tsx     // Preact components Claude defines on first use
├── components.css     // their styles
└── plans/
    ├── 2026-05-13-1430-add-oauth.plan.tsx

When Claude needs a kind not in the kit (say db.schema), it appends a component to components.tsx, then imports it in the plan. Future plans in that project can reuse it. The viewer auto-resolves the import; no build step beyond the in-memory esbuild transform.

Comments — one per block, nothing else

Each block has a tiny toolbar: + comment if empty, edit comment if a comment exists. Clicking opens a popover anchored to the block with a single textarea. Submitting writes the comment; submitting again overwrites it. No author, no timestamp shown, no reactions, no replies, no resolve, no delete. The point is a quick "this needs attention" stickynote, not a discussion thread.

MCP tools

ToolPurposeReturns
wait_for_message BLOCKING Block until a message arrives (browser chat, wp send, or "Send feedback"). No timeout. {text, source, payload?}
ask_user BLOCKING Push structured questions; modal in UI; times out cleanly. {answers} | {timed_out:true}
create_plan WRITE Submit a full .plan.tsx source. Server compiles + validates structure + block ids. {plan_id, url}
update_block WRITE Replace one <Block id="…"> by id. Operates on the JSX source via a CST patcher. {plan_id, block_id}
append_block WRITE Insert a new <Block> at a position. {plan_id, block_id}
register_component WRITE Append a Preact component to the project's components.tsx. Validates it exports a named function. {name}
set_plan_status proposed | approved | implemented | abandoned. {plan_id, status}
set_state Override implicit activity state. {ok}
list_plans / get_plan FAST Read-only views. {…}
open_in_browser Run the open-command against a URL. {ok}

No resolve_comment, no delete_comment, no like_*. Comments overwrite in place via the UI's POST /api/comment. Write tools (create_plan, update_block, append_block, register_component) return plan_frozen if the plan's status is implemented.

The planner agent

---
name: web-planner
description: Interactive planning partner. Triggered by /web-plan. Owns plan
  documents authored as Preact .plan.tsx, asks clarifying questions in the
  browser, and revises in response to inline block comments. Never voluntarily
  ends — always blocks on wait_for_message.
tools: mcp__web-planner__*, Read, Glob, Grep
---

OUTER LOOP, forever:
  1. mcp__web-planner__wait_for_message
  2. Interpret:
     • FIRST message → planning brief. Read the codebase, then call
       create_plan with the full .plan.tsx source.
     • "Feedback on plan …" bundle → patch with update_block /
       append_block. Comments cannot be resolved or deleted.
     • Other → answer or clarify.
  3. If a real decision is needed, call ask_user (or render a
     <DecisionPanel> in a block).
  4. Goto 1.

AUTHORING RULES:
  • Plans are Preact .plan.tsx. Use components from @web-planner/kit.
  • If you need a new block kind, call register_component to add it to
    the project's components.tsx, then import it in the plan.
  • Block ids are stable. Reuse them across revisions. Never drop an id
    that has a comment without addressing it first.
  • Plans with status "implemented" are frozen. Do not attempt to edit
    them — the server will reject. If the user asks for changes to an
    implemented plan, propose a NEW plan that references it.
  • Prefer <Mermaid> / <Sequence> / <Arch> / <Tree> / <Timeline> over
    prose for structural content.
  • Theme value lives in ~/.web-planner/config.json. Read it on the first
    create_plan of a session. If you don't recognize the theme name,
    ask_user for the color intent before authoring.

Interactive installer

install.sh walks through 8 prompts and writes the result to ~/.web-planner/config.json.

  1. Theme — free-form string. Stored verbatim; the planner reads it on first run and either implements it directly or asks follow-ups via ask_user.
  2. Browser open command — e.g. zen-browser --blank-window {url}. {url} is substituted. Empty = print only.
  3. Port — default 1248.
  4. Storage root — default ~/.web-planner/.
  5. Install wp on PATH? — yes/no; if yes, asks the install dir (default ~/.local/bin).
  6. Auto-launch browser on plan create? — yes / only on ask_user / never.
  7. Register MCP in ~/.claude.json? — yes/no.
  8. Register the /web-plan slash command? — yes/no.

Risks & open questions

  • The agent never finishes. If Claude Code enforces a per-tool timeout, wait_for_message dies and the loop breaks. Mitigation: server-side keepalive notifications + auto-reissue.
  • Build step on every plan read. Compile-on-read with esbuild adds ~30-80ms per plan. Cache aggressively by mtime; pre-warm on plan create.
  • JSX CST patching. update_block needs to splice JSX safely. Use a real parser (esbuild's, or Babel) — not regex. Reject patches where the block id isn't found.
  • Mermaid bundle. ~700KB ESM. Lazy-load only when a plan has a <Mermaid> block.
  • Per-project components blast radius. A broken components.tsx breaks every plan in that project. register_component should validate by compiling before saving.
  • Block-id stability. Server rejects writes that drop ids with an attached comment. Planner prompt enforces reuse.
  • Frozen-plan UX. A user trying to edit an implemented plan needs a clear in-UI signal (greyed toolbars, status pill colored differently) — not just a silent server reject.
  • Port collision. Installer asks for an alternate if 1248 is taken; CLI reads from config.
  • Concurrent sessions. v1 doc'd as "one session at a time"; v2 scopes by session id.
